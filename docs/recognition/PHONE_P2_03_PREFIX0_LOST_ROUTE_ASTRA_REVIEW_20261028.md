## Material findings

1. **Old recovery does not unlock the replacement APK.** `CameraOrientationExportAndroid.java:30–37` validates a fixture receipt against the current source/APK and generates fixture bytes from that tuple. `CameraMatrixRecoveryStore.java:22` strictly checks both identities. `CameraOrientationAndroid.java:23–28` requires that current fixture pass for readiness/capture. A legacy recovery therefore requires another current-APK fixture anyway. `CameraOrientationFixture.java:5–12` confirms this is generated metadata/header evidence, with no irreplaceable capture. Historical recovery has little incremental value for the stated objective.

2. **The proposal is an accounting/authority extension, not an existing retry.** `prepare` requires `OWNER` (`ExportAndroid:56`); `selection()` requires the same state (`Store:43`). The existing write engine is appropriately conservative: it consumes WRITE before output and only reconciles read-only afterward (`Engine:26–45`). Keeping that engine is sound. Adding a historical writable descriptor, executor sidecar and a second selection is avoidable complexity here; the 25 model assertions do not implement these boundaries.

3. **The recovery callback design remains incomplete.** A provider result is not proof that a caller's nonce was echoed. Correlation must come from the registered ActivityResult route and independently restored operation state; registration must precede START, and an old callback must fail even if the recovery sidecar is torn. Current `Activity:25–26` has no nonce parameter; `ExportAndroid:57` accepts any matching SELECTION callback. A separate key alone is insufficient evidence. Android explicitly requires callback registration on recreation and separate preservation of additional state: [Activity result documentation](https://developer.android.com/training/basics/intents/result). No promise that a lost task can be resurrected follows from this API.

4. **Crash/grant transitions need exact disposition if recovery is ever chosen.** Launch record before picker means a crash before actual launch still consumes recovery. Callback record before grant/DESTINATION means a crash in that gap cannot reprocess the callback or adopt a grant. A persisted grant without DESTINATION must block/close unverified, with bounded cleanup; any matching grant, including read-only, must trigger the no-orphan rule (`hasGrant(..., true)` alone misses read-only grants). DESTINATION permits only explicit continuation; WRITE permits only readback reconciliation. Missing sidecar outcome must not erase native consumption or manufacture success. Current `Activity:61` auto-continues through `inspect(true)`, and even `inspect(false)` performs terminal grant cleanup (`ExportAndroid:45–51`); neither is a pure status substitute. Use `readStatus` for observation. Persistable access is separately acquired and can be invalidated by document moves/deletion: [Android storage documentation](https://developer.android.com/training/data-storage/shared/documents-files).

5. **Sidecar/identity changes are wider than they appear.** `RecoveryPlan:56–59` rejects extra leaves in the old root; adding records requires an explicit fixed footprint or separate bounded root. Preserve all existing six-step validation and retained read-only prohibitions (`Store:38`). Capacity checks must avoid recursively acquiring the already-held historical lock. `RecoveryAndroid:161–180` establishes selected FD/path identity, not original historical inode continuity; host inode/UID checks and `historicalInodeAttested=false` must remain distinct. Host pre/post checks do not prove absence of every intervening replacement.
