## Confirmed Windows finalization defect

After closing the ZIP and validating count/size, the producer executes
`with pending.open('rb') as f: os.fsync(f.fileno())` before rename/receipt.
On the same pinned Windows Python runtime, this exact operation fails on harmless
generated ZIP bytes with OSError/errno9. A generated counterfactual using a
write-capable r+b handle succeeds, followed by rename and durable receipt write;
generated bytes/hashes remain identical. No actual pending file was flushed,
renamed, written or reprocessed by the counterfactual.

Windows flushing requires a write-capable handle; see
[Microsoft FlushFileBuffers documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).
The deterministic read-only flush defect explains why a closed, correctly sized
pending archive remains after40 successful preparation messages. The historical
raw exception was withheld, so its exact errno is reproduced rather than read
from the original log. Other assembly errors must still fail closed.
